# 影片分析與觀看建議

協助使用者判斷一支影片是否值得投入注意力，保留可供 Notes 整理的分析報告。預設使用繁體中文；依使用者要求調整語言與分析重點。

先讀取 Notes 的 [AGENTS.md](../../../AGENTS.md)，並從 Notes 根目錄執行專案工具。產出報告時使用本 skill 的 [assets/video-summary.md](assets/video-summary.md)；本機工具以實際可用資源為準。

## 輸入與報告位置

- 接受影片／Podcast 網址、本機影片或音訊、字幕、逐字稿，以及對既有報告的個人回饋。
- 網址或檔案路徑已足夠開始；選填用途、主題重點、分析層級。只在無法識別來源或回饋對象時釐清，不要求先填問卷。
- 報告預設保存於 repo 的 `reports/videos/`；使用者指定的位置優先。檔名沿用 `YYYY-MM-DD-video-ID-short-title.md`，日期為首次完成分析日。
- 用平台與穩定影片 ID／canonical URL 找既有報告。同一來源更新原報告，不因網址參數、加入心得或重跑分析再建立一份。沒有平台 ID 的本機來源使用可重用的本機識別，不冒充平台影片 ID。
- 一支影片對應一份獨立報告。批次請求可附排序或集合索引，但不能用一篇總摘要取代逐支報告。

## 分析層級與證據取得

一般「分析這支影片」以完整逐字稿分析為目標；使用者明確要求快速篩選時使用初篩。

- `quick-screen`：依 metadata、說明、章節、創作者摘要或部分字幕判斷。`transcript_coverage` 為 `none` 或 `partial`；推薦與評分是暫定，不重建未取得的論證。
- `full-transcript`：取得並核對涵蓋完整片長的逐字稿，再重建主張與批判分析。記錄核對方法、辨識不確定處；文字覆蓋完整不代表視覺內容也已核讀。

1. 優先取得原始平台的標題、作者、網址、片長、發布日期與章節。未知資料保持未知，不能以分析日代替發布日。
2. 逐字稿優先序：創作者字幕 → 平台字幕 → 可確認對應同一影片的公開逐字稿 → 已授權且工具可用的本機音訊轉錄。
3. 需轉錄時優先使用音訊與現有模型；依實際可用的工具執行。MacWhisper 是可能的工具，不假定它一定有可用 CLI，也不把 GUI 操作成功視為無人值守能力。
4. 完整資料取不到時，交付有實際依據的初篩；在報告「流程紀錄」留下原始分析要求、完整分析尚未完成及缺件，方便之後接續。資料連初篩都不足時，記錄受阻原因與最小缺件，不編造分數或內容。
5. 需要視覺判讀、聲音表現或示範細節時，明確指出仍須看原片。可靠時間碼不存在時只列主題段落。

## 分析與評分

先說明核心主張、推理與證據，再評估實用性、適用條件、反例與限制。明確區分創作者主張、外部查證與助理推論；查證結果附來源及可用的小節／頁碼／時間碼。

重要、低信心或具有重大後果的事實主張，用一手或權威來源核對。無法驗證就保留不確定性，不以影片本身重述作為獨立證明。

保留兩種分數，並使 YAML、篩選結論與品質表一致：

- `recommendation_score`：1–10，是否值得把注意力花在原片。
- `quality_score`：相關性、資訊密度、原創性、來源品質、行動價值各 1–5 分的總和。
- 品質分的預設觀看建議：5–10 `skip`、11–15 `summary-only`、16–20 `selected-sections`、21–23 `full-watch`、24–25 `deep-study`。若依用途或個人判斷覆寫，說明理由。

評估相關性時採用使用者目前用途與已知偏好。使用者主動提供不同主題就是當下興趣的依據，不能只因不在既有偏好清單而扣分。觀看推薦、是否納入知識庫、事實可信度分別判斷。

## 報告交付

- 依範本保留基本資訊、篩選結論、一句話摘要、核心重點、實用性、內容類型、適合觀眾、批判分析、推薦理由、值得看片段、品質評分、依據與限制、實際解讀、個人心得及清理狀態。
- 對已有報告保留使用者原話與有效內容，不為了套格式批量改寫其他報告。
- 首次交付時「看完後的一句話」保持待填。`status: complete` 只表示目前標示的分析層級已完成，不代表使用者看完、同意、入庫或發布。
- 無法取得足夠證據時使用 `status: blocked`，推薦與分數留空；不將受阻紀錄冒充可入庫的完成報告。
- 提供可點擊的報告連結、主要結論、觀看建議與重要限制，並邀請使用者回覆一句話。未收到回覆就結束本次交付，讓下次可接續。

## 使用者回饋與 Notes 交接

回饋可以是自己的理解、取捨或下一步，不要求一定看完整影片。例如「我只讀摘要，想保留驗收方法，下次做工具前先寫驗收條件」可以直接處理。

1. 先辨識是否為具體回饋或更新要求；單純「好／收到」不修改報告，也不為此追問對象。有實際更新意圖時，以來源 ID／網址或已識別的報告確認對象；多份待回饋且無法識別時才詢問。
2. 保存使用者原話與日期；僅記錄實際表達的判斷與行動，不把簡短肯定擴寫成承諾。不推定已觀看，未說明觀看方式就保持 `unknown`。
3. 使用範本中的獨立欄位記錄狀態：`reflection_status` 為 `pending`／`provided`／`declined`；`viewing_status` 為 `unknown`／`not-watched`／`partial`／`full`；`knowledge_action` 為 `pending`／`keep`／`defer`／`skip`。
4. 預設規則：收到具體個人回饋且沒有有效的「略過／暫不入庫／稍後」要求時，將尚未決定的 `knowledge_action` 設為 `keep` 並接續入庫。保留先前已明確設定的取捨，除非使用者更改。明確要求未看先保留時也可入庫；心得仍空白。單純「好」或收到訊息不算具體回饋。
5. 對已完成且選擇 `keep` 的報告，讀取 repo 內 `.agents/skills/llm-wiki-ingest/SKILL.md`，將完整報告路徑交給該流程處理。報告是 `video-report`／`secondary-summary`，必須保留原本覆蓋與信心。若 ingest 不可用，保留交接待辦及原因，不宣稱已完成。
6. 快照、`source_id`、版本去重、來源卡、概念整合、review、Wiki 索引與日誌由 ingest 流程維護。分析或使用者心得有實質更新後，重新交接同一來源的新版本，不算另一份獨立證據。單純補上入庫／發布結果，不觸發再次入庫，避免流程紀錄形成循環。
7. Git commit／push 與提醒交由 repo 已設定的共用流程；沿用有效的既有授權，不重複要求確認。記錄入庫及發布各自的實際結果，失敗時指出已完成與待重試步驟；不因發布失敗重新分析影片。沒有相應流程或可用工具時，明說尚未執行。

## 暫存資料與完成檢查

- 報告目錄不保存下載媒體或完整受版權保護逐字稿。保留分析所需的引用定位與取得方式，不把來源網址寫成已永久保存原始證據。
- 分析與必要追問完成後，只清理本次建立且不再需要的暫存檔；每次以單一明確路徑刪除，不遞迴、不使用萬用字元或批量刪除。不得刪除使用者提供的原檔或 Notes 快照。等候心得本身不是長期保留暫存音訊的理由。
- 交付前核對每支來源都有獨立報告、來源身分正確、必要段落齊全、分數一致、分析層級與覆蓋相符、引用與時間碼有依據、個人狀態沒有被推定。
- 若 repo 已配置影片報告索引器或驗證工具，執行對應檢查；不假定舊影片專案的 `tools/` 已搬入 Notes，也不以 Wiki 索引器替代影片報告驗證。
