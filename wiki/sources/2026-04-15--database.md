# Database

## Summary

Database is an entry-point system-design source about choosing storage systems from requirements rather than from product names. It frames database choice around two independent dimensions: the data model and the workload. It contrasts relational databases, NoSQL families, OLTP, OLAP, and vector databases, then gives interview guidance for reasoning from data shape, query pattern, consistency needs, scale, and operational complexity. The ingest treats product names such as PostgreSQL, DynamoDB, Redis, Cassandra, MongoDB, Neo4j, ClickHouse, BigQuery, Redshift, Pinecone, Weaviate, Milvus, pgvector, Redis VSS, and Elasticsearch as brief examples rather than standalone wiki entities.

## Key Claims

1. Database selection should start by asking what shape the data has and what queries the system must serve. [[database-selection|Database Selection]]
2. Data model and workload are orthogonal dimensions: a database can be relational, document, key-value, wide-column, graph, or vector-oriented while serving OLTP or OLAP needs. [[data-model|Data Model]] [[database-workload|Database Workload]]
3. Relational databases are strong defaults for structured data, SQL queries, joins, constraints, and ACID transaction boundaries, but horizontal scaling and cross-node joins or transactions add complexity. [[relational-database|Relational Database]] [[database-transactions|Database Transactions]] [[database-sharding|Database Sharding]]
4. NoSQL is not one database type; it is a family of systems that trade parts of the relational model or SQL interface for scalability, flexibility, or access-pattern-specific performance. [[nosql-database|NoSQL Database]]
5. Key-value, document, wide-column, and graph databases solve different data-shape and access-pattern problems rather than being interchangeable alternatives to SQL. [[key-value-store|Key-Value Store]] [[document-store|Document Store]] [[wide-column-store|Wide-Column Store]] [[graph-database|Graph Database]]
6. OLTP systems serve high-concurrency business transactions and point reads or small writes, while OLAP systems scan historical data for aggregation and analysis. [[oltp|OLTP]] [[olap|OLAP]]
7. Vector databases support similarity search over embeddings for semantic search, RAG, image search, and recommendation use cases where exact key lookup is the wrong abstraction. [[vector-database|Vector Database]] [[vector-index|Vector Index]]
8. Product choice should be justified in terms of workload fit: PostgreSQL for ACID and SQL, DynamoDB for managed low-latency scale, Cassandra for high write throughput, Redis for low-latency key-value and cache-like use cases, and BigQuery or Redshift for OLAP separation. [[database-selection|Database Selection]]

## Notable Quotes

- Page 1: The source frames database choice as a map rather than memorizing feature lists.
- Page 2: The two interview questions are the data's shape and whether the workload is transactional or analytical.
- Page 6: The source warns against starting with a generic SQL-versus-NoSQL comparison.
