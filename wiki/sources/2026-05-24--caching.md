# Caching

## Summary

This source explains caching as placing frequently read, expensive-to-read, or latency-sensitive data in a faster or closer layer than the original source of truth. [[2026-05-24--caching|Caching]] It frames caching as a targeted read-path optimization rather than a default "add Redis" answer: first identify the bottleneck, then decide what data can be cached, where it should be cached, how stale it may be, and what happens on misses or cache failures. [[2026-05-24--caching|Caching]] The source covers cache locations, including CDN, client-side cache, in-process cache, external cache, and database buffer cache, along with cache patterns such as cache-aside, write-through, write-behind, and read-through. [[2026-05-24--caching|Caching]] It also emphasizes failure modes: stampedes, stale cache, hot keys, penetration, avalanche, cache outages, and correctness boundaries where cache must not replace source-of-truth checks. [[2026-05-24--caching|Caching]]

## Key Claims

1. Caching should target a specific read path and bottleneck rather than being applied generically to every piece of data. [[2026-05-24--caching|Caching]]
2. The central caching tradeoff is faster reads and lower backend load versus stale data and additional failure modes. [[2026-05-24--caching|Caching]]
3. Cache design should answer four questions: which read path is being accelerated, how stale the data may be, who rebuilds on a miss, and how the system behaves if cache fails. [[2026-05-24--caching|Caching]]
4. Cache location matters because CDN, client-side, in-process, external cache, and database buffer cache have different latency, sharing, invalidation, and failure characteristics. [[2026-05-24--caching|Caching]]
5. Cache-aside is the common default for application-level Redis/Memcached caching, while CDN behavior resembles read-through caching because the edge fetches from origin on miss. [[2026-05-24--caching|Caching]]
6. TTL is both a memory-management and freshness tool, but it should be combined with invalidation, jitter, stale fallback, or refresh patterns when traffic and correctness require it. [[2026-05-24--caching|Caching]]
7. Correctness-critical decisions such as Airbnb booking inventory, payments, matching engines, and ledgers should use the source of truth for final decisions rather than trusting stale cache. [[2026-05-24--caching|Caching]]
8. Cache observability must go beyond hit rate to include fallback QPS, tail latency, eviction rate, hot-key distribution, stampedes, stale responses, invalidation latency, and origin offload. [[2026-05-24--caching|Caching]]

## Concepts Mentioned

- [[application-level-caching|Application-Level Caching]] — Shared backend cache such as Redis or Memcached between application servers and databases. [[2026-05-24--caching|Caching]]
- [[cdn-and-edge-caching|CDN and Edge Caching]] — Edge caching for static, public, or carefully keyed cacheable responses close to users. [[2026-05-24--caching|Caching]]
- [[client-side-cache|Client-Side Cache]] — Cache stored in browsers, mobile apps, or client libraries. [[2026-05-24--caching|Caching]]
- [[in-process-cache|In-Process Cache]] — Per-application-instance memory cache with very low latency and weak cross-instance invalidation. [[2026-05-24--caching|Caching]]
- [[cache-aside|Cache-Aside]] — Application-managed read cache pattern where misses fall back to source and then refill cache. [[2026-05-24--caching|Caching]]
- [[write-through-cache|Write-Through Cache]] — Write pattern where cache and database are updated synchronously on the write path. [[2026-05-24--caching|Caching]]
- [[write-behind-cache|Write-Behind Cache]] — Write pattern where cache or buffer accepts writes first and flushes to database asynchronously. [[2026-05-24--caching|Caching]]
- [[read-through-cache|Read-Through Cache]] — Cache layer fetches from origin on miss rather than making the application do it. [[2026-05-24--caching|Caching]]
- [[freshness-budget|Freshness Budget]] — The product-specific staleness tolerance that drives TTL and invalidation choices. [[2026-05-24--caching|Caching]]
- [[cache-invalidation|Cache Invalidation]] — Strategies to update, delete, version, or purge cached data after writes. [[2026-05-24--caching|Caching]]
- [[ttl-jitter|TTL Jitter]] — Randomizing expiration times to prevent many keys from expiring together. [[2026-05-24--caching|Caching]]
- [[stale-while-revalidate|Stale-While-Revalidate]] — Returning stale data while refreshing in the background. [[2026-05-24--caching|Caching]]
- [[request-coalescing|Request Coalescing]] — Allowing only one request or worker to rebuild a missing hot key. [[2026-05-24--caching|Caching]]
- [[cache-warming|Cache Warming]] — Proactively loading or refreshing likely-hot cache entries before demand arrives. [[2026-05-24--caching|Caching]]
- [[cache-stampede|Cache Stampede]] — Many simultaneous misses on a hot key overwhelm the backend. [[2026-05-24--caching|Caching]]
- [[cache-penetration|Cache Penetration]] — Repeated misses for nonexistent keys reach the backend. [[2026-05-24--caching|Caching]]
- [[negative-caching|Negative Caching]] — Caching "not found" results briefly to protect source systems. [[2026-05-24--caching|Caching]]
- [[cache-avalanche|Cache Avalanche]] — Many keys expire together and create a backend traffic spike. [[2026-05-24--caching|Caching]]
- [[hot-key|Hot Key]] — One cache key or object receives enough traffic to overload one cache node or serving path. [[2026-05-24--caching|Caching]]
